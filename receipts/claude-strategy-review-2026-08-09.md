# Claude Strategy Review — Brand Agent Portfolio + ADLC (2026-08-09)

## VERDICT: PROCEED-WITH-REVISE

The foundation (schema, cards, ADLC stage model, gates) is well-formed and internally consistent — it validates clean, the safety rails are real, and the thesis ("Agent Card = soul, SDKs = bodies") is the right call. But it ships two P0 problems: it doesn't reconcile with this repo's own stated identity, and its "EVAL" gate is currently theater (structural check only, no live pass-rate). Fix those before calling this the SSOT and building GenCreator-Studio integration on top of it.

---

## What is strong

- **Schema discipline.** `agent-card.schema.json` is tight: `additionalProperties: false` everywhere, conditional `allOf` rules correctly force `parent_host_id` on specialists and restrict `private_vault` memory to non-public surfaces. This is the single best artifact in the drop — it's the thing that actually prevents a bad card from shipping.
- **Fail-closed default.** `memory_scope: private_vault` → surfaces restricted to `hermes/cli/telegram` is enforced at both schema level (JSON Schema conditional) and script level (`validate_agent_cards.py:54-57`) — belt and suspenders, correctly redundant.
- **Persona law is coherent and matches known Frank doctrine.** One host per brand, specialists as chips, L5 swarm gated behind human approval — consistent with `CLAUDE.md` parallel-agents protocol and the "artifact score" language already used elsewhere in the estate.
- **All 8 cards + 3 eval suites are schema-valid and soul_md files exist on disk** — I ran `validate_agent_cards.py` and `run_eval_suite.py` live; both return exit 0. This is not vaporware — the artifacts are real and internally cross-referenced correctly (card `soul_md` paths resolve, `evals.suite_id` paths resolve, KB pack paths resolve).
- **Non-goals section (`BRAND_AGENT_PORTFOLIO.md:73-80`) is doing real work** — "144 public faces," "native apps before PWA," "public L5 swarms without proof gates" are exactly the failure modes this kind of project usually walks into. Keeping it in the same doc as the plan (not a separate aspirational doc) is right.
- **10h plan has real stop rules** (disk TIGHT, private vault leak, dirty branch → doc-only) — this is a plan that has clearly been burned before and encodes the scar tissue.

## What will fail in production

### P0 — Blockers

1. **This repo doesn't know what it is.** `README.md` and `AGENTS.md` (untouched by this branch) describe the repo's entire purpose as: Codex control plane + Hermes profiles + OpenClaw gateway + DeepAgents harnesses + SIS memory/provenance. Neither file mentions Agent Cards, ADLC, brand portfolios, Gen-Ω, or any of the new concepts. The new work lives in `docs/agent-portfolio/`, `docs/adlc/`, `docs/execution/`, `cards/`, `kb-packs/`, `schemas/` — none of it is linked from README's Quickstart table or AGENTS.md's "What This Repo Is" section, and none of the pre-existing docs (`docs/swarm-roles.md`, `docs/control-plane-workflow.md`, `configs/hermes-profiles.example.json`) reference the Agent Card system either. Two unrelated architectures now cohabit one repo with zero cross-links. Before this becomes "the SSOT" (per `BRAND_AGENT_PORTFOLIO.md:5`), decide: is the Agent Card system a new layer *inside* the existing control-plane/Hermes-profile model, or a replacement for it? Right now a reader hitting README first has no idea this system exists, and a reader hitting the portfolio doc has no idea Codex/OpenClaw/DeepAgents exist. Update README + AGENTS.md to at minimum link forward, or state explicitly that Agent Cards are the new identity layer riding on top of the existing Hermes-profile/OpenClaw runtime split.

2. **The EVAL gate is not a gate — it's a lint check.** ADLC (`ADLC.md:19`) requires "Golden prompts, refusal tests, brand voice, leak tests" with "Pass rate threshold" before SHIP, and the Definition of Done requires "Eval suite green at tier bar." But `scripts/run_eval_suite.py` only checks that eval JSON files are structurally valid (has `cases`, has `id/prompt/expect` keys, card file exists) — it never invokes a model, never grades a response, never computes a pass rate. There is no harness anywhere in this repo that actually runs the golden prompts against a live agent and scores them. Every card currently marked `"status": "active"` (all 8) has therefore never cleared its own EVAL gate in any real sense. This is the single biggest gap between "looks done" and "is done" in the whole drop — fix this before shipping any card as `active` in a customer-facing surface (Gen-Ω, FrankX Concierge).

3. **`gen-visual`, `gen-hook`, `gen-ship` reference eval suites that don't exist.** Each card sets `evals.suite_id` (e.g. `evals/gen-visual.v1.json`) but only `gen-omega.v1.json`, `frankx-concierge.v1.json`, and `starlight-operator.v1.json` exist under `evals/`. `run_eval_suite.py` only iterates existing files, so it silently reports "3/3 valid" instead of flagging the 5 missing suites for cards marked `active`. Combined with finding #2, three of five P0 specialists are `active` with a dangling, never-created quality gate. Either the validator needs to cross-check every card's `evals.suite_id` resolves to a file (the way it already does for `soul_md` and `public_kb`), or these cards should not be `status: active` yet.

### P1 — Improvements

4. **Identity/SDK split is sound in principle, weak in enforcement.** The SDK law table (`BRAND_AGENT_PORTFOLIO.md:21-29`) says cards are the soul and SDKs are bodies — good. But nothing in the schema, the load contract, or the validator enforces that a *second* runtime (e.g. someone bootstrapping a raw OpenAI Agents SDK or Google ADK backend) can't silently fork identity by embedding its own system prompt instead of pulling `soul_md`. `WEB_LOAD_CONTRACT.md` only documents the Vercel AI SDK path; there's no equivalent contract for "if you build an ADK backend, here's how you must load the card" — meaning the "not brand soul home" rule for ADK is aspirational prose, not a structural constraint. Given this is explicitly called out as an "optional backend," it will get built by someone in a hurry and quietly drift from the card. Worth a one-paragraph "ADK integration contract" mirroring `WEB_LOAD_CONTRACT.md` before any ADK lane is enqueued.

5. **Public/private memory boundary has one loophole: `handoffs`.** `starlight-operator.json` (private_vault, L4) lists a handoff `{"to": "gen-omega", "when": "public product studio work should run under GenCreator card"}` — correct in direction. But nothing in the schema or `WEB_LOAD_CONTRACT.md` specifies what happens to *conversation context* on a handoff. If a Hermes session (private_vault memory) hands off to a public-surface specialist, does context/history cross the boundary? The load contract's step 7 ("Specialists: host sets active_specialist_id... on complete return to host") says nothing about memory scope truncation across a handoff. This is exactly the kind of seam where a private detail leaks into a public transcript. Add an explicit rule: handoff never carries private_kb/private_vault content across a memory_scope boundary, only the structured task packet.

6. **Brand sequencing (P0/P1/P2) is reasonable but the eval min_pass_rate ordering is backwards.** `starlight-operator` (private, operator-only, L4) requires the *highest* bar (0.95), `frankx-concierge` (public-facing, thin) requires 0.9, and `gen-omega` (public-facing, deepest surface area, L3, most tool access) requires the *lowest* bar (0.85). If the risk model is "public-facing + broad tool access = higher blast radius," Gen-Ω should arguably carry the highest bar, not the lowest, since it has the largest `tools_allow` list and is the first real product surface. Confirm this ordering was intentional (e.g. "internal tooling must be near-perfect because Frank has zero tolerance for friction on his own operator") rather than an artifact of copy-paste.

7. **No test for cross-tenant memory leakage exists yet**, despite `mind.memory_scope` being the single most safety-critical field in the schema and "Tenant memory leak tests: 0 critical" being a named success metric (`BRAND_AGENT_PORTFOLIO.md:120`). `evals/gen-omega.v1.json` has 5 cases, none of which probe "does this agent ever surface another user's project data." Given `gen-omega` has `memory_scope: user` and multi-tenant product surfaces (`web`, `phone_pwa`), this should be case #1 in its eval suite, not absent.

8. **10h plan realism: window 2:30–5:00 assigns Codex a schema validator + eval harness in the same 2.5h slot as Grok doing voice/face critique + experiment design** — these are meant to run in parallel per the lane table, which is fine, but the plan gives no explicit merge/conflict protocol for when Codex's harness changes and Grok's experiment specs both want to touch `experiments/` or `evals/` in the same window. Given the estate's own parallel-agents doctrine (`~/.claude/CLAUDE.md`) mandates "one agent = one branch" and "don't edit a file another live agent is mid-rewrite on," and this plan has 4 lanes writing to the *same repo* concurrently (L-SSOT, L-REVIEW, L-CODEX, L-GROK all target `army-architecture`), there's a real risk of last-write-wins clobbering across those 2.5h. The plan should specify path-level lane ownership (e.g. L-CODEX only touches `scripts/`+`evals/`, L-GROK only touches `experiments/`+prose critique files) — it's implied by the artifact table but not stated as a hard boundary the way the parallel-agents protocol requires.

9. **Multi-runtime parity risk: Hermes adapter says "never blind overwrite Frank's operator SOUL"** (`HERMES_ADAPTER.md:17`) but gives no mechanism to *detect* drift after the initial merge — no checksum, no version pin, no "last synced against card version X" marker in either the card or the live Hermes SOUL. Six months from now, when Frank has hand-edited his live Hermes SOUL a dozen times and someone re-runs the import checklist, there is nothing in this repo that tells them what changed. Add a `metadata.soul_sync_ref` or similar to `starlight-operator.json` pointing at a hash/date of the last confirmed merge.

### P2 — Nice-to-haves

10. `scripts/validate_agent_cards.py`'s `basic_validate` duplicates most of what `jsonschema.Draft202012Validator` already checks (required keys, enum membership) — harmless since it's a fallback path when `jsonschema` isn't installed, but worth a comment noting it's intentionally redundant so a future maintainer doesn't "simplify" it into a bug.
11. `kb-packs/frankx/offers-public.md` and `kb-packs/starlight/operator-core.md` are single-bullet stubs (3-5 lines) — fine for a skeleton per the 10h plan's own scope, but the portfolio doc's success metric table implies these need real content before Gen-Ω/FrankX Concierge go live; flag as known-thin rather than let it look done.
12. No `cards/stewards/*.json` exist yet even though the schema glob (`validate_agent_cards.py:11`) and portfolio doc's steward tier (L4) both anticipate them — `starlight-operator.json` living under `cards/hosts/` instead of `cards/stewards/` despite `tier: "steward"` is a minor taxonomy inconsistency (directory vs. schema `tier` field disagree). Not a validator failure since the validator globs both dirs, but worth normalizing before more steward cards are added.
13. `gen-critic` has `tools_allow` missing `project_write` (correctly — it's read-only, which is good specialist design) but this asymmetry isn't called out anywhere as a deliberate pattern; a one-line convention note ("read-only specialists get no `project_write`") in `ADLC.md` would make future card authors copy the right template instead of defaulting to full access.
